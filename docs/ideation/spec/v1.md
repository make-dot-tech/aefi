# Aefi Product Specification

**Status**: Draft
**Last updated**: 2026-08-06

## 1. Overview

**Aefi is the evidence and financial-intelligence layer for agent commerce.**

Aefi connects agent identities, delegated authority, task-level permissions, jobs, payments, outcomes, and supporting evidence so agents and marketplaces can:

* understand economic activity
* evaluate providers and counterparties
* verify payments and job outcomes
* determine whether actions were properly authorized
* make auditable decisions with confidence

Aefi begins with Arc and its agent-commerce ecosystem while remaining extensible to other chains, wallets, runtimes, marketplaces, and authorization systems.

## 2. Core problem

Agent-commerce activity is fragmented across:

* identity and reputation registries
* agent runtimes
* delegated wallets
* authorization systems
* job and escrow contracts
* x402 payments
* signed receipts
* marketplace evaluations
* settlement records
* tool and network activity logs

A payment record can prove that funds moved, but it usually cannot independently answer:

* Which agent initiated the payment?
* Which principal authorized the agent?
* What task was the agent performing?
* What was the agent permitted to do?
* Was that permission still active when the action occurred?
* Which job or service was the payment associated with?
* Was the deliverable accepted?
* How reliably has the provider performed before?
* What evidence supports each conclusion?

Aefi turns these fragmented records into structured, searchable, evidence-backed intelligence.

## 3. Product boundaries

Aefi is not intended to become:

* an identity registry
* a wallet
* an authorization engine
* an agent runtime
* an escrow protocol
* a marketplace
* a general agent framework

Those systems create identities, permissions, jobs, payments, and outcomes.

Aefi indexes, connects, explains, evaluates, and searches the evidence they produce.

```text
identity, wallet and execution systems
-> create authority and activity records

job and payment protocols
-> create economic records

aefi
-> connects those records into financial intelligence
```

## 4. Product principles

### Evidence over assumptions

Every meaningful conclusion should include:

* confidence
* controlled confidence reasons
* supporting evidence
* evidence count
* evidence types
* confidence model version
* known coverage gaps

### Identity is not enough

A verified identity does not prove:

* current authorization
* competence
* reliability
* successful delivery
* compliance with a task's permissions

Aefi combines identity with authority, activity, jobs, payments, outcomes, and historical behavior.

### Authority is contextual

An agent can be generally authorized to spend money while still being unauthorized to perform a particular action during a particular task.

Aefi therefore uses two authority layers:

```text
delegated mandate
-> what the principal generally allowed the agent to do

task execution authority
-> what the agent was allowed to do during this specific run and at this exact action
```

### External evidence outranks self-reporting

Evidence directly emitted by wallets, contracts, authorization engines, runtimes, tool mediators, and network enforcement points should carry more weight than an agent's own description of what it did.

Cloudflare's Agent Access Model similarly places task identity, enforcement, capability state, and activity logging outside the model itself. It describes short-lived task credentials, per-action authorization, a capability ceiling that can only narrow during a task, and an externally generated Agent Activity Log. ([The Cloudflare Blog][1])

### Vendor-neutral core model

Aefi should support concepts introduced by systems such as Cloudflare without making its schema Cloudflare-specific.

For example:

```text
cloudflare term              aefi core concept
task execution graph      -> task_execution
capability ceiling        -> initial_capability_set
trust ratchet             -> capability_transition
agent activity log        -> enforcement_activity
virtual wallet            -> delegated_wallet
```

## 5. Core data model

```text
principal
-> agent identity
-> delegated mandate
-> wallet

principal + agent + task template
-> task execution
-> capability state
-> action
-> authorization decision

service
-> commerce job
-> deliverable
-> evaluation
-> payment
-> outcome
-> reputation

all objects
-> evidence
-> confidence
```

A **task execution** and a **commerce job** are related but distinct:

* A task execution is a runtime and authorization concept.
* A commerce job is an economic agreement for work.
* One job may involve multiple task executions.
* One task execution may perform actions related to multiple jobs.

## 8. Evidence model

### Evidence priority

```text
1. on-chain contract and settlement events
2. authorization and enforcement events
3. wallet and payment-provider records
4. signed receipts and acknowledgements
5. marketplace evaluation records
6. agent or provider self-reports
7. behavioral and wallet heuristics
```

### Evidence object

```json
{
  "evidence_id": "evidence_123",
  "type": "authorization_event",
  "source": "agent_access_system",
  "reference": "event_456",
  "supports": [
    "task_execution_linked",
    "capability_active_at_execution",
    "policy_decision_allowed"
  ],
  "observed_at": "2026-08-05T12:05:03Z",
  "confidence": "high"
}
```

### Mediation and collection coverage

Aefi must not treat missing authorization events as proof that an action was unauthorized.

Cloudflare notes that enforcement logs only cover mediated paths; encrypted traffic, out-of-bound activity, and telemetry failures may create collection gaps. ([The Cloudflare Blog][1])

```json
{
  "mediation_coverage": {
    "status": "partial",
    "observed_channels": [
      "wallet",
      "mcp_tools"
    ],
    "unobserved_channels": [
      "direct_external_network"
    ],
    "known_gaps": [
      "network_telemetry_unavailable"
    ]
  }
}
```

Possible coverage statuses:

```text
complete
substantial
partial
minimal
unknown
```

## 11. Matching rules

### High confidence

* exact job ID in a memo or event
* explicit task execution ID
* task-scoped credential
* authorization decision tied to an immutable action
* ERC-8183 lifecycle linkage
* escrow release following acceptance
* signed completion and acceptance receipts
* explicit delegated-wallet relationship

### Medium confidence

* matching principal, agent, counterparty, amount, and time
* signed off-chain acknowledgement
* matching service reference
* confirmed principal-agent relationship without complete task evidence

### Low confidence

* wallet clustering
* behavioral similarity
* payment-only observation
* inferred provider ownership
* model-generated activity description

## 13. SDK scope

Initial helpers:

```text
format structured payment memo
attach job ID
attach task execution ID
attach agent and principal references
hash deliverables
generate signed completion receipt
generate signed acceptance receipt
describe delegated mandate
describe task capability state
emit structured activity events
validate spending limits locally
```

The SDK should not issue authoritative credentials or replace an authorization engine.

## 14. Behavioral and risk intelligence

Later Aefi may derive explainable signals such as:

* unusual spending velocity
* repeated failed purchases
* attempts outside the current capability set
* frequent policy denials
* actions after task credential expiry
* unexpected counterparties
* unusual provider switching
* payment amounts inconsistent with previous behavior
* increasing rejection or dispute rates
* incomplete mediation coverage
* sudden degradation in provider performance

These should remain evidence-backed observations, not opaque risk scores.

## 16. Success criteria

The MVP is successful when it can reliably:

* map identities to agents and principals
* connect jobs, payments, and outcomes
* explain why a payment occurred
* distinguish mandate authority from task authority
* evaluate authorization at the time of an action
* expose known evidence and collection gaps
* calculate auditable provider-performance metrics
* search providers using structured criteria
* return confidence and evidence with every important conclusion
* expose its functionality through APIs, MCP, and x402
